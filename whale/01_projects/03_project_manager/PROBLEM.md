문제 정의: 03_project_manager

문제
프로젝트 정보가 5개 레포(wiki, AI, FE, BE, CLOUD)에 흩어져 있어서, 매주 월요일 타운홀 문서를 만들려면 문서 탐색, 선별, 취합, 양식 요약 같은 수작업이 듭니다. 최종 목표는 "누가 무엇을 하고 다음 액션은 무엇인지"를 자동 정리하는 것입니다. 다만 긴급성 때문에 타운홀 문서부터 시작하고, 현황과 할 일 관리는 MVP 이후로 미룹니다.

MVP 범위
- 용어: 타운홀 미팅일은 매주 월요일입니다. 서버(GitHub Actions)는 전날인 일요일 20:00(KST)에 실행됩니다. 집계 기간은 지난 일요일 20:00부터 실행하는 일요일 20:00까지 7일이고, 끝 시각은 실제 실행 시각이 아니라 그 일요일 20:00로 고정합니다. 예를 들어 타운홀 미팅일이 2026-10-12(월)이면 집계 기간은 2026-10-04 20:00 ~ 2026-10-11 20:00입니다.
- 입력: wiki 레포에서 제목이 `[Troubleshooting]`으로 시작하고, 생성 시각이 집계 기간 안에 있는 이슈입니다. 열림/닫힘 상태는 따지지 않습니다. 본문 구조는 `# YYYY-MM-DD 오류명`, `## 🐞 에러 내용`, `## 🔍 원인 분석`, `## ✅ 해결 방법`, `## 회고`입니다.
- 실행: 일요일 20:00에 트리거가 발생하면 생성부터 게시까지 한 번에 자동으로 수행합니다. 작성자 username으로 과정(AI/풀스택/클라우드)을 매핑해, 과정별 섹션(`## 과정명`)으로 나눈 본문을 만듭니다. 항목마다 4항목 양식(어려움 / 해결 / 배운 점 / 링크)을 따르고, 집계 대상이 없는 과정은 `(트러블 슈팅 내용 없음)`을 넣습니다.
- 게시: wiki에 `[Townhall] YYYY-MM-DD`(타운홀 미팅일) Issue 1건으로 올립니다. 작성자는 `github-actions[bot]`입니다. 같은 제목의 Issue가 이미 있으면 새로 만들지 않고 종료합니다.
- 검토: 게시 전 검수는 없습니다. 팀원 5명이 게시된 Issue를 보고 월요일 발표 전에 직접 검토하고 수정합니다. 이 검토는 MVP 범위 밖이며 팀이 책임집니다. 알람은 만들지 않고, 팀원이 각자 일요일 20:00에 모바일 알람을 맞춥니다.
- 재실행: Issue가 올라오지 않았으면 Actions의 수동 실행 버튼으로 다시 실행합니다. 본인(쓰기 권한)과 팀장(admin) 모두 가능합니다.
- 구현: 코드는 `KTB4-20th-wiki` 레포 안(`tools/townhall/`와 `.github/workflows/townhall.yml`)에 둡니다. 기존 `01_meeting_docs_summarizer`의 코드를 옮겨서 확장합니다(Gemini, 함수 주입 구조, 양식 검증 재사용). 트리거는 `schedule`(`0 11 * * 0`)과 `workflow_dispatch`이고, GitHub 연동은 기본 `GITHUB_TOKEN`(`issues: write`)과 `gh` CLI로 합니다.
- 키: 팀 공용 Gemini 키를 `GEMINI_API_KEY`라는 Actions Secret으로 등록합니다. 팀장(daniel, admin)이 직접 등록하며, 키 값을 본인(whale)에게 전달할 필요는 없습니다. 로컬 테스트용 키는 본인의 `.env`에 따로 둡니다. 비용 부담은 MVP에서 신경 쓰지 않습니다.

품질 조건
- 발표 보조용 간결한 요약본입니다. 약어는 풀지 않고, 상세 내용은 링크로 연결합니다.
- 배운 점은 이슈의 `## 회고` 섹션에서만 가져옵니다. 회고가 없으면 `(작성 필요: 회고 없음)`으로 비워 둡니다.
- 민감 정보는 정규식 필터로 LLM 앞단에서 `[REDACTED]`로 치환합니다. 허용 도메인은 `github.com/100-hours-a-week/*`뿐입니다. 비난 표현은 프롬프트로 중립화합니다. 출력에 시크릿이 남아 있어도 게시를 막지 않고, 마지막 방어선은 게시 후 팀원 검토입니다.

완료 기준
1. 일요일 20:00에 트리거되면 별도 조작 없이 `[Townhall] YYYY-MM-DD` Issue가 올라갑니다.
2. 모든 항목에 4항목 양식과 원본 링크가 있습니다.
3. 정규식 필터의 `[REDACTED]` 치환이 자동 테스트로 검증됩니다.
4. 같은 제목의 Issue가 있으면 중복 게시되지 않습니다.
5. 사람이 하는 단계가 8개에서 1개(과정별 문서 작성)로 줄고, 이후 검토는 게시된 Issue를 보고 팀이 알아서 합니다.

실패 처리
- 이슈 한 건의 요약이 실패하면 `(요약 실패: 원본 링크)` 자리표시자를 넣고 계속 진행합니다.
- 3개 과정 모두 집계 대상이 0건이면 Issue를 만들지 않고 "대상 없음"으로 종료합니다.
- 실행 자체가 실패하면(키 오류, 한도, 네트워크 등) 알림은 없습니다. 팀원이 일요일 20:00 알람에 Issue 존재를 확인하고, 없으면 수동 실행으로 재실행합니다.

MVP 제외
- 대시보드, 알림, 실시간 갱신, `--week` 옵션
- 게시 전 사람 검수와 확인 프롬프트, 승인 라벨, 과정별 파일 분리(합의에서 철회)
- 집계 기간 이전에 생성되었으나 집계 기간 중에 해결되거나 갱신된 이슈
- 공동 작성이나 여러 과정에 걸친 이슈
- Daily Scrum, PM/PL 미팅 등 다른 문서와 다른 레포의 Issues/PR
- 현황/할 일 관리

남은 가정(틀리면 알려주세요)
- 조직에서 GitHub Actions의 예약 실행이 허용되어 있고, 워크플로를 `main`에 머지할 수 있습니다(브랜치 보호 규칙 확인 필요).
- wiki 레포가 공개(`private: false`)라서 게시된 내용은 누구나 읽을 수 있습니다. 이 위험은 사용자가 책임집니다.
- 팀장이 `GEMINI_API_KEY`를 등록하고, 키는 만료되거나 한도를 넘지 않습니다.
- 팀원 5명이 매주 게시된 Issue를 빠짐없이 검토합니다.

팀장 확인 사항
현재 계정(`whale5500d`)은 wiki 레포에 쓰기(push) 권한만 있고 admin이 아니라서, 아래 항목은 팀장(daniel, admin)이 확인하거나 처리해야 합니다.
1. 팀 공용 Gemini API 키를 발급하고, 레포 Settings → Secrets and variables → Actions에 `GEMINI_API_KEY`로 등록합니다.
2. Settings → Actions → General에서 Actions 사용 가능 여부, 사용 가능한 액션 정책(`actions/checkout` 등 허용), Workflow permissions를 확인합니다.
3. `main` 브랜치 보호 규칙이 있으면 워크플로 PR을 승인합니다. 예약 실행은 `main`의 워크플로만 동작합니다.
4. 팀원 전체에 자동 게시 방식(게시 전 검수 없음, 공개 레포)과 일요일 20:00 확인 절차를 공유합니다.

팀장에게 보낼 요청문
> wiki 레포(KTB4-20th-wiki)에 타운홀 문서 자동 생성 도구를 올리려고 합니다. 매주 일요일 20:00에 GitHub Actions가 지난 한 주의 `[Troubleshooting]` 이슈를 요약해서 `[Townhall] YYYY-MM-DD` Issue를 자동으로 올립니다. 게시 전 검수는 없고, 월요일 발표 전에 팀원이 게시된 Issue를 보고 직접 검토·수정하는 방식입니다. 아래 확인과 작업을 부탁드립니다.
> 1. 팀 공용 Gemini API 키 발급 후, 레포 Settings → Secrets and variables → Actions에 `GEMINI_API_KEY`로 등록 (키 값은 저에게 전달하지 않으셔도 됩니다)
> 2. Settings → Actions → General에서 Actions 사용 가능 여부, 사용 가능한 액션 정책, Workflow permissions 확인
> 3. `main` 브랜치 보호 규칙이 있으면 워크플로 PR 승인
> 4. 팀원 전체에 자동 게시 방식과 일요일 20:00 확인 절차 공유
