## 1. 한눈에 보기

- `/grill-me`로 문제를 먼저 정의한 뒤, 같은 세션에서 로직 개발, wiki 레포 이식, PR 생성까지 진행했습니다.
- 최종 목표는 "흩어진 프로젝트 정보를 모아 누가 무엇을 하고 다음 액션이 무엇인지 자동 정리"하는 것입니다. 긴급성 때문에 **타운홀 미팅 문서 자동 생성**만 MVP로 정했고, 현황과 할 일 관리는 MVP 이후로 미뤘습니다.
- 동작: 매주 일요일 20:00(KST)에 GitHub Actions가 지난 7일의 `[Troubleshooting]` 이슈를 과정별로 요약해 `[Townhall] YYYY-MM-DD` Issue 1건을 **사전 검수 없이 자동 게시**합니다. 팀원이 게시 후 검토합니다.
- 상태: 코드와 테스트는 완료(61개 통과)했고 wiki 레포에 PR #115, #116을 올렸습니다. **GitHub 위에서 예약 실행은 아직 한 번도 돌아가지 않았습니다.**

## 2. 용어 (대화 중 정정을 거쳐 확정)

| 용어 | 정의 |
|---|---|
| 타운홀 미팅일 | 매주 월요일 |
| 실행 시점 | 타운홀 미팅 전날인 일요일 20:00(KST) |
| 집계 기간 | 지난 일요일 20:00부터 실행하는 일요일 20:00까지 7일. 끝 시각은 실제 실행 시각이 아니라 그 일요일 20:00로 **고정**(몇 시에 실행해도 결과 동일). 시작 이상, 끝 미만 |

## 4. 대화 중 정정된 오해 (같은 실수 방지용)

- AX 동아리를 대상으로 가정함 → 부트캠프 팀 프로젝트가 맞음.
- 타운홀 독자를 팀 내부로 가정함 → 다른 6개 팀 약 30명 포함.
- `--week` 옵션을 제안함 → 타운홀은 매주 월요일이므로 불필요.
- "이번 주/이전 주" 표현이 기준 없이 쓰임 → 타운홀 미팅일 기준의 집계 기간으로 통일.
- 실행 시점을 월요일 직전 시점으로 오해함 → 일요일 20:00.
- "연속적으로 수행"을 자동 `publish`로 읽을지 여부 → 사람이 실행하는 것으로 확인했다가, 이후 D20으로 서버 자동 게시로 전환.
- 게시 Issue의 작성자는 본인이 아니라 `github-actions[bot]`.
- "회고 섹션 제목에 `회고`가 들어간다"는 개발자 용어 표현이었음 → 실제 템플릿 제목이 정확히 `## 회고`임을 확인해 가정 해소.

## 6. 검증한 것과 못 한 것

**검증함**

- 실제 wiki 레포를 읽기 전용으로 조회해 `--dry-run`으로 본문 생성 확인(집계 기간 2026-09-27 20:00 ~ 10-04 20:00의 5건). 원문과 대조한 3건(#84, #85, #97)에서 지어낸 내용 없음.

- GitHub Actions에서 PR 테스트 워크플로 성공(Actions 사용 가능, 허용 액션 정책 통과).

**검증하지 못함**
- 예약 워크플로(`townhall.yml`)는 GitHub 위에서 한 번도 실행되지 않음. `issues: write` 권한 부여 여부 미확인.
- 실제 `gh issue create` 경로는 가짜 실행기로만 검증. 실제 Issue를 게시한 적 없음.
- 요약 품질은 5건 한 번의 실행 기준. 모델 출력은 실행마다 달라질 수 있음.
