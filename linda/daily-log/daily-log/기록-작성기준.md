# 기록 작성기준 — 일기 · 트러블슈팅

**일기나 트러블슈팅을 쓰기 전에 이 문서를 먼저 읽는다.** 기기와 세션이 달라도 같은 기준으로 쓰기 위한 문서다. 함께 쓰는 규칙은 볼트의 `CLAUDE.md`(R1 사실 창작 금지 · R2 수치 근거)다.

> *"그 글만 읽고도 그날 무슨 일이 있었고 어떤 문제가 어디서 발생해서 어떻게 해결했다, 아니면 어떻게 논의했다 정도로 자세하게, 하지만 쉽게 읽히도록"*

---

## 1. 기준 8가지

| # | 기준 | 뜻 | 점검 질문 |
|---|---|---|---|
| 1 | **혼자 읽힌다** | 다른 파일·대화를 열지 않아도 이해된다. "상세는 raw/기타 참조"로 넘기지 않는다 | 이 글만 읽은 사람이 무슨 일인지 설명할 수 있나? |
| 2 | **맥락이 먼저** | 무엇을 하던 중이었는지부터 쓴다 | 첫 문단에 "무엇을 하려고 했나"가 있나? |
| 3 | **어디서** | 파일·서비스·단계를 구체적으로 적는다 | "어디서" 생긴 문제인지 적혀 있나? |
| 4 | **어떻게 알았나** | 에러 메시지, 로그, 누가 발견했는지 | 발견한 경로가 적혀 있나? |
| 5 | **왜** | 원인을 한 단계 더 판다. 증상만 쓰지 않는다 | "왜 그랬나"에 답이 있나? |
| 6 | **어떻게 풀었나 · 논의했나** | 해결했으면 방법을, 못 풀었으면 논의와 결론을, 미해결이면 **미해결**이라고 쓴다 | 지금 상태를 알 수 있나? |
| 7 | **용어를 풀어준다** | 처음 나오는 전문용어는 괄호로 한 번 설명한다 | 비전공자가 읽다가 막히는 단어가 없나? |
| 8 | **한 문장에 한 가지** | 짧은 문장. `→`·약어만 늘어놓은 메모체 금지 | 소리 내어 읽을 수 있나? |

> **자세함 ≠ 길이.** 커밋 해시·줄 번호를 늘어놓는 것은 자세한 게 아니다. **사건의 흐름**(상황 → 문제 → 발견 → 원인 → 해결 → 배운 것)이 빠짐없이 있는 게 자세한 것이다.
> 해시·URL은 문장 속이 아니라 끝의 `근거` 한 줄로 모은다.

## 2. 트러블슈팅 구조

틀은 볼트의 `_템플릿/트러블슈팅.md`. 제목 단계는 **`###` 사건 제목 → `####` 소제목**이다 (`##`가 사건 아래로 오면 목차가 깨진다).

| 소제목 | 쓸 것 |
|---|---|
| 무슨 상황이었나 | 그때 무엇을 하던 중이었나. 관련된 시스템을 한 줄로 소개 |
| 무엇이 문제였나 | 증상. 어디서 · 어떤 모습으로 |
| 어떻게 알았나 | 에러 메시지 · 확인한 명령 · 누가 발견했나 |
| 왜 생겼나 | 원인. 기술 원인 + **내 판단에서 빠진 것** |
| 어떻게 해결됐나 (또는 논의했나) | 한 일 · 비교한 안 · 결론. 미해결이면 **미해결**과 다음 조치 |
| 배운 것 | 다음에 달라질 행동 1~3개. 일반론 금지 |
| 근거 | PR·이슈 링크, 커밋 해시 (포인터로만) |

**스택이 안 터져도 트러블슈팅이다.** 전제가 틀려 도구를 바꾼 판단, 코드를 쓰기 전에 미리 발견한 불일치도 넣는다.

### 좋은 예 / 나쁜 예

**❌ 나쁜 예** — 한 줄 메모. 이 글만 보면 무슨 일인지 모른다.

```md
## 🐞 에러 내용
- S3_BUCKET 필수화 → compose 누락
## ✅ 해결 방법
- PR #13으로 해소 (edfa6db, 28cd557)
```

**✅ 좋은 예** — 이 정도 자세함이 기준이다.

```md
### S3_BUCKET 환경변수가 빠져 서버가 켜지지 않을 뻔한 문제

#### 무슨 상황이었나
문서 인덱싱(검색할 수 있게 문서를 잘게 나눠 저장하는 작업) 기능을 만들면서,
파일을 저장할 S3 버킷 이름(`S3_BUCKET`)을 반드시 입력해야 하는 설정으로 바꿨다.
전에는 값이 없으면 기본값을 썼는데, 잘못된 곳에 저장되는 걸 막으려고 기본값을 없앴다.

#### 무엇이 문제였나
팀 서버를 띄우는 설정 파일(`compose.yaml`)에는 `S3_BUCKET` 항목이 없었다.
그대로 배포했다면 배포는 "성공"으로 끝나는데 API 서버만 켜지지 않았을 것이다.

#### 어떻게 알았나
배포 전날 내 브랜치를 팀 브랜치 위로 옮기기 전에, 팀 설정 파일에서 `S3_BUCKET`을 검색해 봤다. 0건이었다.

#### 왜 생겼나
내 코드 안에서는 "필수로 바꾼 것"이 안전한 변경이었다.
하지만 그 값을 넣어 주는 쪽(배포 설정)까지 확인하지 않았다. 테스트는 내 코드만 보니까 잡을 수 없었다.

#### 어떻게 해결됐나
다음 날 오전, 팀원의 PR #13(저장소 구조 재정리)이 설정 파일을 손보면서 `S3_BUCKET`도 함께 들어갔다.
지금은 값이 없으면 서버를 띄우는 단계에서 "S3_BUCKET을 넣으세요"라는 메시지와 함께 바로 멈춘다.

#### 배운 것
- 설정을 필수로 바꾸면, 그 값을 넣어 주는 배포 설정까지가 내 작업 범위다.
- 이번엔 남의 PR이 우연히 고쳐 줬다. 내가 적어 둔 문제를 내가 끝까지 추적하지 않았다.

#### 근거
PR #13 · 커밋 `edfa6db` · `origin/main:compose.yaml:34`
```

## 3. 일기 구조

틀은 볼트의 `_템플릿/일일노트.md`. **일기 본문은 에이전트가 쓰는 글이다.** 내가 직접 쓴 것은 `## 내 메모`에만 두고 에이전트는 그 칸을 고치지 않는다.

| 섹션 | 필수 | 쓸 것 |
|---|---|---|
| `## 오늘의 맥락` | ✅ | 지금 무슨 프로젝트의 어느 단계인가. 오늘 무엇을 하려고 했나. 2~4문장 |
| `## 오늘 한 일` | ✅ | 일 단위로 `###` 소제목. 각 일마다 **무엇을 · 왜 · 어떻게 · 결과**. 빈칸 금지 — 확인된 일이 없으면 "확인된 작업 없음"과 이유 |
| `## 논의한 것` | 있으면 | 회의·리뷰·팀원과 정한 것. **누가 무엇을 제안했고 무엇으로 정했나.** 팀원 발언은 팀원 것으로 표시 |
| `## 오늘의 트러블슈팅` | 있으면 | §2 구조 그대로. **요약으로 줄이지 않는다** |
| `## 수치` | 실측 있을 때만 | §4 판별 질문을 통과한 값만. 없으면 섹션을 만들지 않는다 |
| `## 회고` | ✅ | **하루에 한 번만.** 오늘 가장 중요했던 판단 1개와 다음에 다르게 할 것. 트러블슈팅별 배운 것과 중복 금지 |
| `## 이어서 확인할 일` | 있으면 | 미해결 · 막힌 것 · 내일 할 것 |
| `## 내 메모` | 나 | 내가 직접 쓰는 칸. **에이전트 수정 금지** |
| auto 마커 두 쌍 | 자동 | 스크립트가 채우는 근거 표. 본문을 대신하지 않는다 |

> **auto 마커 안의 표는 근거이지 일기가 아니다.** 표만 있고 본문이 비어 있으면 그날 기록은 없는 것과 같다.

## 4. 수치 — 판별 질문 하나

> **"시스템이 얼마나 빠르고 · 정확하고 · 무거운지를 잰 값인가, 아니면 내가 얼마나 일했는지를 센 값인가?"**
> 앞쪽이면 `## 수치`에 넣는다. 뒤쪽이면 넣지 않는다.

| ✅ 수치다 (시스템을 잰 값) | ❌ 수치가 아니다 (작업량을 센 값) |
|---|---|
| 응답 시간 · 지연 (p50·p95) | 커밋 개수 · 푸시 횟수 · PR 개수 |
| 처리량 (건/초) | 추가·삭제 줄 수 (`+413/−262`) |
| 정확도 · 재현율 · 검색 적중률 | 바꾼 파일 수 |
| 메모리 사용량 · 이미지 크기 · 기동 시간 | **테스트 개수** (`119 passed`) |
| 비용 (원·토큰) | 문서 줄 수 변화 (`457→522줄`) |
| 전후 비교가 있는 개선 폭 | 커밋 해시 (근거 포인터일 뿐) |

- 테스트 개수는 **통과했다는 사실**만 문장으로 쓴다. "전체 테스트 통과" ⭕ / "## 수치 — 119 passed" ❌
- 수치에는 **어떻게 쟀는지**(도구·조건·데이터 크기)를 같이 적는다. 조건 없는 숫자는 면접에서 무너진다 (R2)
- 추정값은 수치가 아니다. 실제로 잰 값만

## 5. 쓰기 전 · 쓴 뒤 체크리스트

| 시점 | 확인 |
|---|---|
| 쓰기 전 | 이 문서를 읽었다 · 그날 근거(보드·세션·트러블슈팅 원문)를 모두 읽었다 |
| 쓴 뒤 | 이 글만 읽고 그날을 설명할 수 있다 |
| 쓴 뒤 | `## 오늘 한 일`이 비어 있지 않다 · `## 회고`가 한 번뿐이다 |
| 쓴 뒤 | 트러블슈팅마다 6개 소제목이 모두 있다 · 미해결이면 미해결이라고 썼다 |
| 쓴 뒤 | `## 수치`에 작업량이 없다 (§4) |
| 쓴 뒤 | 처음 나오는 전문용어에 괄호 설명이 있다 |
| 쓴 뒤 | 원본에 없는 사실을 지어내지 않았다 (R1). 모르면 `> [!question] 확인 필요` |
