# 일일회고 자동작성 에이전트

첫 실행에 개인 설정과 사용할 폼 주소를 확인한다. 이후에는 오늘 날짜 Daily Scrum·Troubleshooting으로 학습 내용과 성과를 쓰고, 의견 항목에는 매번 다르게 고른 긍정 문구를 넣는다. 사전채움(prefill) 링크를 기본 브라우저로 열면 사용자가 확인하고 제출한다.

아래 `<스킬폴더>`는 이 SKILL.md가 있는 실제 디렉터리다. 전역 설치 링크로 호출됐을 때도 작업 디렉터리에 `.claude/skills/`가 있다고 가정하지 말고, 링크 원본의 스크립트와 `config.json`을 쓴다.

## 절대 규칙

- **학습 요약과 성과 이유는 실제 기록으로 쓴다.** 기록이 없으면 그 칸은 비운다. 실제로 하지 않은 실습·질문·성공을 만들어 넣지 않는다.
- **자동 의견은 긍정적인 표현으로만 채운다.** `feedback.py`의 문구를 쓰며, 강사·교육에 대한 비판이나 불만을 덧붙이지 않는다. "아쉬웠던 점"도 배움을 더 이어가고 싶다는 긍정적인 기대로 표현한다.
- **개선점은 앞으로 실천할 목표로 쓴다.** 기록에 근거가 있으면 "테스트를 못 했다" 대신 "테스트를 작업 과정에 꾸준히 포함하겠습니다"처럼 앞으로의 행동으로 표현한다. 근거가 없으면 스크립트가 고른 일반적인 학습 목표를 쓴다. 성취한 사실처럼 쓰지 않는다.
- **직접 지정한 값이 가장 우선한다.** 사용자가 그날 문구·평점·빈칸을 지정하면 무작위 문구 대신 해당 값을 쓴다.
- **`[확인필요]` 같은 플레이스홀더 표시를 값에 넣지 않는다.** 그대로 제출돼 버린다.
- **제출은 사람이 한다.** 어떤 경우에도 제출 버튼을 대신 누르지 않는다. 링크를 열어주고, 표로 보여주고, 사람이 누른다.

## 0. 설정 — 첫 실행에 네 가지를 묻는다

스킬 폴더의 `config.json` 이 있으면 읽어서 재사용한다. **없으면 먼저 제안값을 받아온다:**

```bash
python3 <스킬폴더>/scripts/bootstrap.py --suggest
```

`gh` 활동 기록으로 계정·팀·과정을 추측하고, 커밋 author 이름으로 이름 후보를 만들어 JSON 으로 돌려준다. `gh` 가 없으면 `brew install gh` 로 설치하고, 인증이 없으면 안내 후 종료 코드 2 로 멈춘다(이 경우 회고 작성을 진행할 수 없다).

그 다음 **네 가지를 한 번에 묻는다. 추측값을 그냥 쓰지 말고 반드시 확인받는다** — `gh` 가 다른 계정으로 인증돼 있거나 여러 팀 레포에 활동 기록이 있으면 추측이 틀린다:

> 처음이라 설정을 만들겠습니다. 네 가지만 확인해주세요 (괄호는 추측값입니다):
> 1. GitHub 계정 — `kkkk2058` 맞나요?
> 2. 팀 번호 — `13` 맞나요?
> 3. 소속 과정 — 인공지능 / 풀스택 / 클라우드 중 (`인공지능`)?
> 4. 폼에 쓰는 이름 — `영어닉네임 (한글이름)/과정` 형식으로 정확히 알려주세요. (`sehoon.kim (한글이름)/인공지능` 형태로 추측됩니다)

답을 받으면 저장하고 바로 회고 작성을 이어간다:

```bash
python3 <스킬폴더>/scripts/bootstrap.py \
  --github-username kkkk2058 --team 13 --course 인공지능 \
  --name "sevan.kim (김세훈)/인공지능"
```

네 값이 다 들어오지 않으면 스크립트는 **아무 파일도 쓰지 않고** 종료 코드 3 으로 제안값을 돌려준다. 팀 번호는 1~20, 과정은 세 개 중 하나여야 하고, 이름에 `(한글이름)` 같은 자리표시자가 남아 있으면 거부한다 — 그대로 폼에 제출되면 안 되기 때문이다. 팀 번호와 과정에서 스크럼 레포와 강사 폼이 결정되므로 틀리면 엉뚱한 강사에게 후기가 간다.

사람이 터미널에서 직접 `bootstrap.py` 를 실행하면 같은 네 가지를 프롬프트로 물어본다 (제안값은 Enter 로 수락).

**의견은 기본적으로 `feedback_mode: "positive_random"`으로 생성한다.** 설정에 이 키가 없는 기존 사용자도 동일하게 동작한다. 이전 `defaults`의 공통 의견 문구 대신 무작위 긍정 문구를 쓰고, 평점 기본값은 유지한다. 첫 실행에는 자동으로 고른 초안이므로 제출 전에 확인하면 된다고 한 번 알린다. 고정 문구를 원하는 경우만 `feedback_mode`를 `fixed`로 바꾸고 `defaults`에 저장한다.

요일에 따라 제출할 폼이 다르므로 `form_url` 하나를 config에 고정하지 않는다. 강사별 폼 주소는 config의 `form_urls`(강사 이름 → URL)에 저장해 두고 쓴다:

| 강사 | 과정(화/수/목) | 담당 팀(월/금) |
|---|---|---|
| 케빈 | 풀스택 | 1~6팀 |
| 알렉스 | 인공지능 | 7~13팀 |
| 찰리 | 클라우드 | 14~20팀 |

**폼 주소는 이 표(SKILL.md)에 쓰지 않는다.** 이 스킬은 공개 레포에 올라가 있고, SKILL.md 는 커밋되지만 `config.json` 은 `.gitignore` 에 있어 커밋되지 않는다. 1단계에서 고른 강사의 주소가 `config.form_urls` 에 없으면 그때 한 번만 사용자에게 후기 폼 URL을 물어보고(부트캠프 공지에 있다), 받은 주소를 `config.json` 의 `form_urls` 에 저장한 뒤 이어간다.

목록에 없는 과정/강사가 나오면 이 표에 행을 추가하고 (모두가 같이 쓰는 표), 주소는 같은 방법으로 `form_urls` 에 저장한다.

## 1. 날짜와 폼 자동 결정 (질문 없음)

```bash
date "+%F %u %A"   # %u: 1=월 ... 7=일
```

- **화·수·목(2,3,4)** → `course`에 해당하는 강사 폼
- **월·금(1,5)** → `team_number`가 속한 범위의 강사 폼
- **토·일(6,7)** → 수업일이 아니므로 **이때만** 어느 날짜로 쓸지 물어본다

사용자가 날짜를 직접 지정했으면 그 날짜의 요일로 판단한다.

## 2. 기록 읽기 — `gh` CLI로만 (브라우저로 github.com 열지 않는다)

브라우저로 github.com을 열면 새 사이트 접근 권한 프롬프트가 뜨고, 팀원 환경에 따라 거부돼 막힌 사례가 있었다.

```bash
gh issue list --repo <daily_scrum_repo> --search "[Daily Scrum] <MM/DD>" --state all
gh issue view <번호> --repo <daily_scrum_repo> --json title,comments \
  --jq '.comments[] | select(.author.login=="<github_username>") | .body'

gh issue list --repo <troubleshooting_repo> --search "[Troubleshooting] author:<github_username>" --state all --limit 10
gh issue view <번호> --repo <troubleshooting_repo> --json title,body,comments
```

**빈 템플릿 판별:** 이슈 본문이 `# YYYY-MM-DD 오류명` 이나 `## 회고\n-` 처럼 **플레이스홀더만 있고 실제 내용이 없으면 근거로 쓰지 않는다.** 헤딩 아래가 `-` 하나뿐이거나 비어 있으면 없는 것으로 취급한다. (Daily Scrum의 "회고"도 마찬가지 — 비어 있으면 "오늘 한 일"에 적힌 실제 메모에서만 끌어온다.)

소스 우선순위: Daily Scrum → Troubleshooting → (설치돼 있으면) screenpipe `activity-summary`.

**칸마다 근거를 찾는다.** Daily Scrum에 "오늘 한 일"은 있는데 "회고"가 비어 있으면 같은 날짜 Troubleshooting의 교훈도 읽는다. 학습 요약과 성과 이유는 한 일 중심으로 긍정적으로 쓰고, 개선점은 기록의 교훈을 앞으로의 실천 목표로 바꿔 쓴다. 기록에 없는 성취를 더하거나 실패·부족함을 평가하는 문구를 넣지 않는다.

`gh`가 없거나 인증이 안 돼 있으면 `gh auth login` 을 안내한다. `API rate limit exceeded` 면 몇 분 뒤 재시도하면 된다고 한 번 알리고, 계속 재시도하며 시간 끌지 않는다.

## 3. 긍정 의견 생성 + answers.json 작성

먼저 의견 초안을 생성한다. 사용자 설정을 재생성하지 않는다:

```bash
python3 <스킬폴더>/scripts/feedback.py --config <스킬폴더>/config.json --output feedback.json
```

`assets/positive-feedback.json`의 항목별 후보 중 직전 실행과 같은 문장을 제외하고 무작위로 고른다. 직전 선택은 개인 `.feedback-state.json`에 저장하며 커밋하지 않는다. 서로 다른 사용자 사이의 중복까지 보장하지는 않는다.

`feedback.json`을 바탕으로 교육과정·날짜·이름·기록 기반 학습 요약·성과 이유를 더해 `answers.json`을 만든다. 기록 기반의 긍정적인 개선 목표가 있으면 일반 목표를 덮어쓰고, 없으면 생성된 목표를 유지한다. 사용자가 직접 준 값은 마지막에 덮어쓴다. `--overrides user-overrides.json`으로 직접 지정한 값의 JSON을 넘겨도 된다.

`_sources`는 출처 표시용이다. 기록이나 사용자 값으로 덮어쓴 항목의 출처도 함께 바꾸고, `_`로 시작하는 키는 실제 폼 답변에서 제외한다. 키는 **폼 질문 라벨의 고유한 부분 문자열**이다 (entry ID는 하드코딩하지 않는다).

```json
{
  "교육과정명": "<config.course>",
  "수업일": "2026-09-18",
  "이름": "<config.name>",

  "오늘 학습한 내용": "<Daily Scrum '오늘 한 일' 기반, 폼 자수제한 이내>",
  "스스로 개선하거나": "<기록에서 끌어온 긍정적인 실천 목표. 근거가 없으면 feedback.json의 목표>",
  "본인의 성과 평점을 남기신 이유": "<기록 기반>",

  "아쉬웠던 점": "<feedback.json>",
  "좋았던 점": "<feedback.json>",
  "강사에 대한 피드백": "<feedback.json>",
  "교육/세미나에 대한 평점": "<feedback.json의 평점>",
  "교육/세미나 평점을 남기신 이유": "<feedback.json>",
  "오늘의 본인의 성과에 대한 평점": "<feedback.json의 평점>",
  "비고": ""
}
```

주의:

- **이유 문장에 점수 숫자를 쓰지 않는다** (`"7점으로 평가했습니다"` 금지). 사용자가 점수를 바꾸면 바로 앞뒤가 안 맞는다.
- **성과 이유는 기록에 있는 한 일로 긍정적으로 쓴다.** 평점 숫자는 무작위로 바꾸지 않고 설정값 또는 사용자가 지정한 값을 쓴다.
- **비고는 사용자가 요청한 내용이 없으면 비운다.** 자동으로 운영 이슈나 부정적인 평가를 넣지 않는다.

라벨을 모르면 먼저 확인한다:

```bash
python3 <스킬폴더>/scripts/prefill.py --form "<form_url>" --list
```

## 4. 링크 생성 + 브라우저 자동 실행

```bash
python3 <스킬폴더>/scripts/prefill.py --form "<form_url>" --answers answers.json
```

스크립트가 폼 HTML에서 entry ID를 뽑아 라벨로 매칭하고, URL 인코딩·날짜 분해(`_year`/`_month`/`_day`)·선택지 검증까지 한 뒤 **사용자 기본 브라우저로 링크를 연다** (`--no-open` 으로 끌 수 있음). 기본 브라우저에는 보통 구글 로그인 세션이 있으므로 바로 제출할 수 있다.

띄어쓰기 차이는 무시하고 매칭한다. 라벨 키가 0개 또는 2개 이상 문항에 걸리면 스크립트가 에러로 멈춘다 — 조용히 엉뚱한 칸에 들어가지 않는다. 그때는 `--list` 로 라벨을 보고 키를 더 구체적으로 고친다.

**클릭·타이핑 자동화는 쓰지 않는다.** (탭 인식 실패, 드래프트 자동복원, 권한 프롬프트 등으로 과거에 반복 실패했다.)

## 5. 확인 — 제출은 사람이

브라우저 도구(`mcp__Claude_Browser__*` 등)가 있으면 같은 링크를 열어 값이 실제로 들어갔는지 확인한다. 장문형은 페이지 텍스트에 안 나오므로 값으로 직접 읽는다:

```js
[...document.querySelectorAll('input[type=text],textarea,input[type=date]')].map(e=>e.value)
```

평점(선형배율)은 별 채움형이라 `[role=radio][aria-checked=true]` 가 1..N 개 잡히면 **N점이 선택된 것**이다. 단 **평점 위젯은 지연 렌더링돼서 navigate 직후 조회하면 빈 배열이 나온다** — 빈 배열이면 잠깐 기다렸다 한 번 더 조회하고, 그래도 비어 있을 때만 실패로 판단한다:

```js
await new Promise(r=>setTimeout(r,1500));
[...document.querySelectorAll('[role=radio]')].filter(e=>e.getAttribute('aria-checked')==='true').map(e=>e.getAttribute('data-value')).join(',')
```

그다음 채팅에 표로 정리해 보여주고, 각 행의 출처를 밝힌다. 자동 선택 문구를 사용자가 직접 쓴 말이나 기록으로 표시하지 않는다:

| 항목 | 값 | 출처 |
|---|---|---|
| 오늘 학습 요약 | ... | Daily Scrum #97 |
| 강사 피드백 | ... | 긍정 문구 자동 선택 |
| 개선 목표 | ... | 기록에서 정리한 실천 목표 / 긍정 목표 자동 선택 |

마지막으로 남은 일을 한 줄로 알린다: **열린 폼에서 자동 선택 문구를 확인하고, "응답과 함께 이메일 주소 기록"을 체크한 뒤 제출.** (이메일 체크박스는 계정 로그인에 연동돼 있어 prefill 대상이 아니다.)

같은 회고의 수정 요청에는 `answers.json`의 해당 값만 바꿔 4단계를 다시 돌린다. 다른 문구도 새로 골라달라고 할 때만 의견 생성기를 다시 실행한다. 사용자가 앞으로 고정 문구를 원하면 `feedback_mode`를 `fixed`로 바꾸고 `config.defaults`를 갱신한다.
